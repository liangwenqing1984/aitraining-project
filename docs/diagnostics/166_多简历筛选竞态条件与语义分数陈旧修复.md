# 多简历筛选竞态条件与语义分数陈旧修复

## 概述

修复多简历上传筛选的两个深层 bug：文件级上传并发竞态致同文件重复添加、旧简历缺少结构化字段时语义相似度不更新。

## 一、handleFileChange 文件级竞态去重

### 需求/问题
Element Plus `el-upload` drag 模式下 `on-change` 事件可能以不同 `uid` 重复触发同一文件。此前 `processingUids` Set 按 `file.uid` 去重，但两个重复事件携带的 `uid` 可能不同，导致两个 API 调用同时发出。同名同大小文件的两路并发都先通过 API 前检查（都未在 `parsedResumes` 中），最终同一简历被重复添加，筛选结果出现混乱数据。

### 修复
新增 `pendingFileKeys` Set，以 `` `${raw.name}_${raw.size}` `` 作为文件内容级去重键，在 API 调用 **前** 检查并锁定：

- 进入函数时先检查 `fileKey`，已存在则直接 return（不发出 API）
- API 调用无论成败，`finally` 中释放 `fileKey`
- `processingUids` 仍保留作为第一道 uid 级防线
- `10MB` 上限检查失败时也清理 `processingUids`

### 关键文件
- `ResumeScreening.vue` — `handleFileChange` 函数

## 二、旧简历语义相似度不更新

### 需求/问题
旧简历（结构化解析功能上线前入库的）缺少 `desiredPosition`、`skills` 等结构化字段，`buildResumeDiscriminativeText()` 返回空字符串。此后代码直接回退到数据库预存 `embedding` 字段 — 该向量是入库时用原始全文生成的，与 `rawText` 效果相同但不会体现模型更新。更关键的是逻辑优先级错了：预存向量 > 实时 rawText 生成，导致每次筛选都返回同样的旧分数。

### 修复
调整 `matchingService.ts` 中 embedding 生成的三级回退顺序：

1. **结构化区分文本**（`discriminativeText` 非空时）→ 最优，岗位方向区分度高
2. **原始文本实时生成**（`rawText` 存在时）→ 次优但保证每次重新计算
3. **预存向量兜底**（仅当以上两者都不可用时）→ 兼容无 rawText 的极旧数据

原来顺序为 1 → 3 → 2，修复后为 1 → 2 → 3。

### 关键文件
- `matchingService.ts` — `screenResumeAgainstJobs` 函数 embedding 逻辑

## 验收清单

- [x] 同文件并发上传不会产生重复解析条目
- [x] 旧简历（无结构化字段）上传筛选时语义相似度重新计算，不再返回陈旧分数
- [x] 多份不同简历筛选结果各自独立，不交叉混编
