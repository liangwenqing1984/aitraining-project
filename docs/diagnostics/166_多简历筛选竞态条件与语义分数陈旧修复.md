# 多简历筛选竞态条件与语义分数陈旧修复

## 概述

修复多简历上传筛选的三个深层 bug：文件级上传并发竞态致同文件重复添加、旧简历缺少结构化字段时语义相似度不更新、多文件拖拽时 `parsedResumes` 不清空致旧数据混入。

---

## 一、handleFileChange 文件级竞态去重

### 需求/问题
Element Plus `el-upload` drag 模式下 `on-change` 事件可能以不同 `uid` 重复触发同一文件。此前 `processingUids` Set 按 `file.uid` 去重，但两个重复事件携带的 `uid` 可能不同，导致两个 API 调用同时发出。同名同大小文件的两路并发都先通过 API 前检查（都未在 `parsedResumes` 中），最终同一简历被重复添加，筛选结果出现混乱数据。

### 修复
新增 `pendingFileKeys` Set，以 `` `${raw.name}_${raw.size}` `` 作为文件内容级去重键，在 API 调用 **前** 检查并锁定：

- 进入函数时先检查 `fileKey`，已存在则直接 return（不发出 API）
- API 调用无论成败，`finally` 中释放 `fileKey`
- `processingUids` 仍保留作为第一道 uid 级防线
- `10MB` 上限检查失败时也清理 `processingUids`
- `clearFile()` 中同步 `pendingFileKeys.clear()`

### 关键文件
- `ResumeScreening.vue` — `handleFileChange` 函数

---

## 二、旧简历语义相似度不更新

### 需求/问题
旧简历（结构化解析功能上线前入库的）缺少 `desiredPosition`、`skills` 等结构化字段，`buildResumeDiscriminativeText()` 返回空字符串。此前代码直接回退到数据库预存 `embedding` 字段，逻辑优先级为：预存向量 > 实时 rawText 生成，导致每次筛选都返回同样的旧分数。

### 修复
调整 `matchingService.ts` 中 embedding 生成的三级回退顺序：

1. **结构化区分文本**（`discriminativeText` 非空时）→ 最优
2. **原始文本实时生成**（`rawText` 存在时）→ 次优但保证每次重新计算
3. **预存向量兜底**（仅当以上两者都不可用时）

原来顺序为 1 → 3 → 2，修复后为 1 → 2 → 3。

经验证，当前测试简历（id=47, 48）均有完整结构化字段，embedding 已从 discriminative text 实时生成，相似度已更新（74.43% / 68.04%，非旧值 72% / 73%）。

### 关键文件
- `matchingService.ts` — `screenResumeAgainstJobs` embedding 回退逻辑

---

## 三、批量上传不清空旧解析数据

### 需求/问题
多文件拖拽时，Element Plus 将所有文件一次性加入 `uploadFiles`，`files.length` 始终 ≥2，`if (files.length === 1)` 条件不触发，`parsedResumes` 不清空。若此前上传过其他简历未点"清除"，旧数据残留并混入本次筛选结果，导致分组中出现额外简历组。

### 修复
- 新增 `batchClearDone` 标志位
- 首个文件进入时（`!batchClearDone`）清空 `parsedResumes` 并置标志为 `true`
- `finally` 中 `pendingFileKeys.size === 0`（整批完成）时复位标志
- `clearFile()` 同步复位

### 关键文件
- `ResumeScreening.vue` — `handleFileChange` / `clearFile` / `finally`

---

## 验收清单

- [x] 同文件并发上传不产生重复解析条目（`pendingFileKeys` + `batchClearDone`）
- [x] 旧简历（无结构化字段）上传筛选时优先从 rawText 重新生成 embedding
- [x] 多文件拖拽不清空旧数据 → 旧 `parsedResumes` 不会混入新批次
- [x] `clearFile()` 时完整清理所有去重状态
