# 简历筛选三个 Bug 修复

## 概述

简历筛选功能上线后陆续发现三个问题：Ollama Embedding 超长文本 500 错误、SQL 占位符参数数量不匹配、匹配结果显示"未知职位"。本文记录每个问题的根因和修复。

---

## 一、Ollama Embedding 超长文本 500 错误

### 现象
上传 PDF/Word 简历后，后端报错 `Ollama Embedding API 错误 (500): {"error":"the input length exceeds the context length"}`，匹配失败。

### 根因
`nomic-embed-text` 模型上下文窗口 8192 tokens，简历文件解析出的文本往往超过此值。最初尝试在 Ollama API 请求中加 `truncate: true` 参数让模型自动截断，但该参数仅对 `/api/generate` 和 `/api/chat` 端点有效，**对 `/api/embeddings` 端点无效**，被 Ollama 静默忽略。

### 修复
在 `embeddings.ts` 的 `generateEmbedding` 入口统一截断至 **2000 字符**：

```typescript
const MAX_EMBED_CHARS = 2000;
function truncateForEmbedding(text: string): string {
  if (text.length <= MAX_EMBED_CHARS) return text;
  const truncated = text.substring(0, MAX_EMBED_CHARS);
  console.log(`[Embedding] 文本过长截断: ${text.length} -> ${MAX_EMBED_CHARS} 字符`);
  return truncated;
}
```

`generateEmbedding` 是所有 embedding 调用的唯一入口，因此覆盖了职位向量化、语义搜索、简历匹配等全部场景。

### 涉及文件
- `services/llm/embeddings.ts` — 新增 `truncateForEmbedding`，在 `generateEmbedding` 中统一截断

## 二、SQL 占位符参数数量不匹配

### 现象
修复超长文本截断后，简历匹配报错 `bind message supplies 4 parameters, but prepared statement "" requires 5`。

### 根因
在清理冗余截断代码时，`matchResume` 和 `uploadAndMatch` 的 `.all()` 调用参数漏传了一个。SQL 中实际有 5 个 `?` 占位符：

| 位置 | 占位符 | 值 |
|------|--------|-----|
| SELECT | `?::vector` | vectorStr |
| WHERE | `?::vector` | vectorStr |
| WHERE | `?` | minSimilarity |
| ORDER BY | `?::vector` | vectorStr |
| LIMIT | `?` | limit |

SELECT 子句的 `1 - (je.embedding <=> ?::vector)` 也是一个占位符，修复前只传了 4 个参数（`vectorStr, minSimilarity, vectorStr, limit`），缺少了 SELECT 对应的 `vectorStr`。

### 修复
补全参数：`.all(vectorStr, vectorStr, minSimilarity, vectorStr, limit)`，同时修正注释说明 5 个占位符。

### 涉及文件
- `controllers/ragController.ts` — `matchResume` 和 `uploadAndMatch` 两处参数修正

## 三、匹配结果显示"未知职位"

### 现象
上传简历匹配到的结果全部显示"未知职位"，职位名称和公司名称为空。

### 根因
`sp_job_enrichments`（增强表）不包含 `job_name`/`company_name` 字段，这些字段在向量化索引时通过 `rawDataMap` 从 `sp_jobs` 表查询。当 `sp_job_enrichments` 的 `job_id` 和 `sp_jobs` 的 `job_id` 不完全匹配时，`rawDataMap` 查找失败，写入空字符串。

数据库写入逻辑：
```typescript
// raw.jobName 来自 sp_jobs（查找可能失败）→ ''，
// row.jobName 来自 sp_job_enrichments（无此字段）→ undefined
raw.jobName || row.jobName || ''  // 最终为 ''
```

### 修复
在匹配查询 SQL 中通过 `COALESCE` + `LEFT JOIN sp_jobs` 做三层兜底：

```sql
SELECT
  je.job_id,
  COALESCE(NULLIF(je.job_name, ''), j.job_name, '未知职位') AS job_name,
  COALESCE(NULLIF(je.company_name, ''), j.company_name, '') AS company_name,
  COALESCE(NULLIF(je.work_city, ''), j.work_city, '') AS work_city,
  ...
FROM sp_job_embeddings je
LEFT JOIN sp_jobs j ON je.job_id = j.job_id AND je.task_id = j.task_id
```

取值优先级：向量表已有名称 → sp_jobs 原始数据 → 兜底默认值。`company_name` 和 `work_city` 同理。

### 涉及文件
- `controllers/ragController.ts` — `matchResume` 和 `uploadAndMatch` SQL 重写
